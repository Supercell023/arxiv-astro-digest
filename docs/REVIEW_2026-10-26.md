## 项目目标和架构

项目将 arXiv、Crossref 和研究资讯整理成面向个人研究者的中文邮件：选择相关论文、提供可回查的事实、按画像评论，并展示近邻方向和日程。

技术栈为 Python、urllib/XML/SMTP、Jinja2、PyYAML、pypdf、OpenAI 兼容客户端。本地配置使用 DeepSeek。没有数据库；状态和反馈通过 JSON，知识和来源通过 YAML 保存。Actions 负责定时调度和回写状态。

基线数据流：配置/日历 → arXiv 自适应抓取 → Crossref 合并 → Zotero → 规则排序/反馈 → 分批摘要 → 两阶段精读 → RSS/Indico → 脉搏/雷达/翻译 → **保存状态** → 渲染 → SMTP。

模块划分适合单用户每日任务；未发现直接模块循环依赖。主要问题是副作用提交时机和数据契约，而非缺少微服务、数据库或设计模式。

需求依据优先采用当前 README、CHANGELOG 和配置说明。PRODUCT_PLAN 混合了早期设计和路线规划；修订版、社区信号等规划没有直接作为当前版本的已承诺功能。

## 重要缺陷登记

## 安全、可靠性与性能边界

- 本机反馈和 Apps Script 示例使用无鉴权 GET 写操作，存在公开写入、跨站请求和链接扫描污染条件；未执行真实攻击。
- Zotero 标题和标签会进入模型请求。是否敏感依赖用户库，应清楚说明外发范围。
- PDF 无大小限制、无可终止的解析时限；先遍历全部页面再切片。存在资源风险，未进行破坏性压测。
- 主 arXiv 故障提前中止其他内容；仅有局部来源降级。
- API 无服务端日期条件，新内容可能耗尽页数预算。隔离样例返回零篇，真实漏抓规模未测。
- SMTP 无 timeout，预检没有检查用户名和密码。
- thinking 参数未充分按供应商隔离；请求构造已验证，真实 OpenAI 返回未测。
- 当前已跟踪文件的有限密钥模式检查未命中，`.env` 未跟踪；未做完整 Git 历史秘密扫描。
- 性能只做静态判断：串行网络、重复抓取、重复分析、没有 Stage A 缓存。不能声称达到特定吞吐或成本。
- JSON 原子替换有价值，但不能解决跨进程读改写冲突或 SMTP 与磁盘之间的事务。
