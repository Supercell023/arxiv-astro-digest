## 2. 项目概览

**类型**：Python 3.11 批处理型日报/周报生成器 + GitHub Actions 定时投递。

**规模**：48 个 Python 文件（`selfcheck.py` 1100 行、`pipeline.py` 926 行、`analysis.py` 645 行）、9 份 YAML 配置、107 项离线测试、26 项自检。

**数据流**：

```
env → Config（355 行，逐项校验）
  → run_pipeline(persist_state=False)            # 只准备，不消费
      arXiv（分页/自适应窗口） + Crossref（期刊闸门） + RSS/Indico
      → Zotero 库（相似度/库内扣分） → rank(ScoreBreakdown)
      → 反馈存储（本地 json + Sheet CSV 合并） → 兴趣闸门
      → 截断（deep+brief） → 中文摘要（LLM 分批）
      → 两阶段评估（抽取事实 → 评估 + 数值回查）
      → 脉搏/雷达 → render_email_html
  → send_email
  → commit_delivery()                            # 只有这里消费 seen/editions
  → state.json 回写 + CI 远端合并提交
```

**外部依赖 7 个**：arXiv API、Crossref、RSS/Indico、OpenAI 兼容 LLM、SMTP、Zotero API、Google Sheets。除 SMTP 外均可缺失，且都有超时、上限与降级路径。

**部署**：`.github/workflows/daily-arxiv-digest.yml`（248 行），cron `30 5 * * *` + 手动触发；action 全部钉到官方 commit SHA；job 级权限最小化；state 回写带 3 轮 fetch/reset/merge/push 重试。

## 4. 缺陷与风险清单

### 4.1 P2（4 项）

#### P2-1 预览会覆盖生产快照 `digest.json` 【已验证】

- **证据**：`pipeline.py:915` 在 `_run_pipeline` 内无条件调用 `_write_digest_json(config.digest_json_path, ...)`，未看 `preview`；`main.py:61-74` 的 `--out` 分支只写 HTML 并更新诊断。
- **放大点**：`scripts/feedback_server.py:216` 与 `scripts/feedback.py:97` 默认都用同一个 `DIGEST_JSON_PATH` 解析投票元数据。
- **影响**：本地跑一次预览 → `digest.json` 变成预览内容 → 之后再点旧邮件的反馈按钮，票的标题/作者/分类挂到错误论文上（`history` 学错方向），或以"没有该 id"降级为学不到。
- **建议**：预览时不写生产快照（或写 `digest.preview.json`）。
- **置信度**：高；**触发条件**：设置 `DIGEST_JSON_PATH` 且本地 `--out`。

#### P2-2 周报跨本地午夜可重复投递 【复查后判定：非缺陷】

- 原怀疑：`editorial.py:29-30` 的 key 含 `start:end`，`pipeline.py:810` 只按 key 去重，23:59 与次日 00:30 各触发一次会发两封。
- **复查结论**：窗口本身随日期滚动。23:59 触发时窗口是 `[周日-7, 周日)`；00:30 触发时是 `[周一-7, 周一)`，两者相差一天、内容不同，属于两个不同窗口，不是"同一份内容重复投递"。同一窗口的重复触发仍被相同 key 拦住。
- **残留行为说明**：若显式设置 `DIGEST_EDITION=weekly`（而非 `auto`），每次运行都会生成滚动 7 天窗口，连续多天运行会连续发"周一至周日各不同"的周报——这是显式配置的语义，不是缺陷，但应在文档中说明。
- **结论**：不改去重键（改键反而会在升级后重发一次，并可能吞掉合法窗口）。

#### P2-3 CI 状态回写依赖 best-effort 诊断文件 【已验证（代码路径）】

- **证据**：`pipeline.py:917-921` 写 `run_report.json` 失败只 `LOGGER.warning`；workflow 第 228 行无条件传 `--report run_report.json`；`scripts/merge_state.py:24-26` 直接 `json.loads(...)` 并取 `report["date"]/["timezone"]`，未捕获 `FileNotFoundError/KeyError/JSONDecodeError`。
- **影响**：邮件已发出，但 state 未回写 → 下次重复推送同一批论文。
- **建议**：`merge_state.py` 对缺失/损坏 report 容错，回退到 `--today`/`--timezone` 或 `DIGEST_TIMEZONE` + 当前日期。
- **置信度**：高；**实际触发**：磁盘满、权限异常等小概率。

#### P2-4 分析阶段失败无显式计数与告警 【已验证】

- **证据**：`pipeline.py:156-198` 的 `_maybe_analyze` 整体 `except` 只 warning 并返回原 papers；`analysis.py:642` 单篇同样只 warning。
- **缓解事实**：`report["analyzed_papers"]`（`pipeline.py:908`）可与 `deep_papers` 对比发现降级，因此不是完全不可见。
- **建议**：report 增加 `analysis_failures` 计数并在 >0 时 warning。
- **置信度**：高。

#### P2-5 发布阻断：整套测试与新脚本尚未入库 【已验证】

- **证据**：`git status --short` 中 `tests/`、`scripts/feedback_server.py`、`scripts/google_feedback.gs`、`scripts/merge_state.py`、多份新 docs 均为 `??`；而 workflow 的 selfcheck job 要跑 `python -m unittest discover -s tests` 与 `node tests/check_google_feedback.cjs`。
- **影响**：若只提交 tracked 文件的修改而不 `git add` 这些未跟踪文件，CI 会在 selfcheck job 直接失败。
- **建议**：提交前 `git add tests scripts/*.py scripts/*.gs docs/…`。
- **置信度**：高。

## 7. 科研/数值专项

- **数值可回查**：`evidence.py` 用 Decimal 做"模型输出 ⊆ 原文"的子集判定，把 `10^{n}` 展开、区间拆成两端点、允许 `±/%` 后缀。局限：只校验"数字出现过"，不校验单位、量纲、语义方向（"从 10^14 降到 10^13" 与 "升到" 都通过），VALIDATION 已如实标注。
- **公式/精度**：项目不做科学计算，只做抽取与核对，无浮点累积与误差传播问题。
- **可复现性**：`extract/assess` 用 `temperature=1.0`，同输入不同输出属设计选择（编辑型产品），不能当可复现基准；`eval_analysis.py` 的 build/run/check 已闭环。
- **数据泄漏**：无监督训练，无泄漏面；`source_text/source_sha256/source_scope` 落盘，可追溯每条结论来自摘要还是全文节选。
